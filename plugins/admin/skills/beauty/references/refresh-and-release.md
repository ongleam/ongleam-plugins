# 검증·반영·예약

자동 지표의 최신화만 요청한 경우 재배포하지 않는다. 이 절차는 소스 또는 AI 근거 파일이 변경됐을 때 적용한다.

## 빌드와 게시

저장소의 `apps/beauty`를 SSOT로 사용한다. 지정 Bun과 root lockfile로 해당 변경 범위의 checks와 실제 localhost 흐름을 확인한다. 매 게시마다 최신 SSOT에서 새 정적 빌드 `bun run build:beauty`를 성공시킨다.

코드·스킬 변경은 사용자 요청과 저장소 PR/release 절차를 따른다. 같은 소스 커밋의 새 `out/`을 release archive에 포함한다. bucket·CloudFront distribution·도메인은 Terraform `static_hosting.beauty`에서 읽는다. 해시 자산을 먼저 업로드한 뒤 HTML을 갱신하고 이전 해시 파일을 즉시 삭제하지 않는다.

workflow 수락이나 파일 업로드만으로 완료 처리하지 않는다. 정적 소스 커밋과 서비스 revision을 확인하고 운영 URL에서 로그인·조직·조회 기간·수치·요청한 변경을 다시 읽는다. 실패를 성공이나 0건으로 대체하지 않는다. 관리자 토큰과 자격 증명을 정적 파일·shell 인자·로그에 넣지 않는다. 다른 checkout이나 과거 산출물을 배포 원본으로 사용하지 않는다.

자동 지표 최신화에 서비스 release를 강제하지 않는다. 실제 원문 근거나 코드 변경이 필요한 경우에만 검증한 새 산출물을 배포한다. 최신 dev와 진행 중인 release·검색 유지보수를 확인하고 동시 변경을 보존한다.

## 정기 실행

사용자가 요청한 경우에만 기존 일정을 확인해 생성·수정한다. cloud에서도 같은 skill·SSOT·Bun·MCP 연결과 저장 권한이 필요하며 로컬 홈/인증 캐시에 의존하지 않는다. 먼저 실제 조회→저장→재조회·게시로 환경을 검증한다. 요청 수락과 실행 성공을 구분하고, 변경 없음은 조용히 유지하며 의미 있는 변경·실패·사용자 조치만 알린다.

범위와 조회 기준은 [워크플로](workflows.md), 완료 기준은 [체크리스트](checklist.md)에 둔다. 앱의 `config/refresh-workflow.md`도 이 skill을 참조하도록 유지한다.
